# 顺达财务核销系统设计

- 日期：2026-07-27
- 状态：已批准（2026-07-28）
- 部署目标：群晖 DSM，Docker Compose
- 第一使用人：财务
- 只读使用人：老板

## 1. 背景与目标

顺达目前通过税务平台导出发票、银行账户明细、微信账单及单独 PDF 凭证进行财务核对。数据分散在多个文件中，常见工作包括：

- 检查顺达开出的发票是否已经收到款项；
- 检查顺达收到的发票是否已经支付；
- 将一张发票与一笔或多笔收付款对应；
- 将多张发票与一笔收付款对应；
- 处理部分付款、预收预付、跨月开票、红冲、退款和代收账户；
- 查找未匹配资金、长期未收款、已付款未收票及疑似重复记录；
- 为老板提供资金、应收、应付和风险 dashboard。

第一期建设一个独立核销台账。系统负责标准化导入、提供候选和保存证据链，但不自动确认核销，也不使用期末余额推断某张发票对应哪笔付款。

## 2. 设计原则

1. 原始数据不可修改：每条正式台账记录必须能追溯到原始文件和导入批次。
2. 实际发生额优先：发票只能与银行或微信的实际资金发生额核销。
3. 余额不作为匹配依据：期初或期末余额可用于报表，但不能替代逐笔资金证据。
4. 人工确认：系统可以提供候选、连续日期合计和差额提示，最终关系必须由财务确认。
5. 金额不重复占用：同一张发票或同一笔资金的累计分配金额不得超过其可核销金额。
6. 操作可逆但不可抹除：撤销、退款和红冲使用反向记录，不物理删除历史。
7. 先核销后扩展：第一期不引入出入库、运输业务单据、付款审批和自动记账。

## 3. 第一阶段范围

### 3.1 包含

- 财务与老板两类账号权限；
- 全部历史数据的分年度迁移；
- 销项发票 Excel 导入；
- 进项发票 Excel 导入；
- 银行 XLS/XLSX/CSV 明细导入；
- 微信 Excel/CSV 明细导入；
- 发票 PDF 批量上传并按发票号码自动关联；
- 付款申请、结算单等通用附件；
- 客户、供应商、税号、银行户名、微信名称和代收账户别名；
- 逐笔核销；
- 结算批次核销；
- 应收、应付、未匹配资金、账龄和异常清单；
- 老板只读 dashboard；
- 操作日志、Excel 导出、数据库及附件备份。

### 3.2 不包含

- 出入库单和运输单据；
- 应开未开发票检查；
- 税控平台或银行 API 直连；
- 自动生成会计凭证；
- 付款申请审批流；
- 原生手机 App；
- 系统自动确认核销。

这些能力可以在核销台账稳定后接入，不改变核心数据模型。

## 4. 用户与权限

### 4.1 财务

可以导入文件、查看原始附件、维护往来单位和别名、创建核销、创建结算批次、撤销核销、处理异常及导出数据。

### 4.2 老板

只能查看 dashboard、汇总报表和异常明细，不能导入、核销或修改数据。完整银行账号默认脱敏，原始附件默认不可下载。

## 5. 技术架构

系统采用适合 DSM 的单体架构：

```text
浏览器
  |
DSM HTTPS 反向代理
  |
Django Web 应用
  |-- PostgreSQL
  |-- DSM 持久化附件目录

DSM Task Scheduler
  |-- 每日数据库备份
  |-- 每日附件备份
```

Docker Compose 第一阶段只包含两个核心服务：

- `web`：登录、导入解析、核销、报表、导出和管理页面；
- `db`：PostgreSQL。

不在第一阶段引入 Redis、消息队列或独立前端 SPA。长时间导入可以先采用后台任务表与页面轮询；数据量证明有需要时再拆分 worker。

建议持久化目录：

```text
/volume1/docker/shunda-finance/
  postgres/
  uploads/
  exports/
  backups/
```

图表采用 ECharts，页面采用 Django 模板和轻量交互，优先保证财务表格的密度、筛选效率和可读性。

## 6. 导入流程

1. 用户选择数据来源并上传文件；
2. 系统保存原始文件并计算 SHA-256 校验值；
3. 识别文件模板并映射标准字段；
4. 数据进入暂存区；
5. 执行必填字段、数据类型、公司户名、日期范围和重复校验；
6. 用户查看有效、重复及异常条数；
7. 用户确认后，有效记录进入正式台账；
8. 异常行留在隔离区，批次保持“未完成”状态，直到修复或明确忽略；
9. 系统保存导入人、确认时间、源文件和错误报告。

去重规则：

- 发票优先使用“发票号码 + 销售方税号”；
- 银行和微信优先使用交易单号；
- 无交易单号时，使用“资金账户 + 时间 + 收支金额 + 对方信息”的组合指纹；
- 同一文件重复上传不得产生第二份正式记录。

## 7. 核心数据模型

| 实体 | 职责 |
|---|---|
| `User` | 财务或老板账号及权限 |
| `Counterparty` | 客户或供应商标准名称、税号和状态 |
| `CounterpartyAlias` | 银行户名、微信名称、银行账号及代收账户关系 |
| `ImportBatch` | 一次导入的来源、范围、状态和统计 |
| `SourceFile` | 原始文件、校验值、存储位置和文件类型 |
| `Invoice` | 销项/进项、发票号、日期、价税合计、红冲及作废状态 |
| `MoneyTransaction` | 银行/微信、收入/支出、金额、时间、交易号及原始对方信息 |
| `Attachment` | 发票 PDF、付款申请、结算单等凭证 |
| `SettlementBatch` | 某往来单位在某结算期间的发票和资金集合 |
| `Reconciliation` | 一次由财务确认的核销操作 |
| `ReconciliationAllocation` | 某张发票从某笔资金分配的具体金额 |
| `Reversal` | 红冲、退款或核销撤销产生的反向关系 |
| `AuditLog` | 操作人、时间、对象和变更内容 |

发票和资金的“未核销、部分核销、已核销”状态由有效分配金额计算，不依赖人工维护的状态字段。

## 8. 核销模式

### 8.1 逐笔核销

用于普通往来单位。财务选择一张或多张发票，再选择一笔或多笔银行/微信资金，填写或确认每条分配金额。

支持：

- 一张发票对应一笔资金；
- 一张发票对应多笔资金；
- 多张发票对应一笔资金；
- 多张发票对应多笔资金；
- 部分核销；
- 跨月核销。

### 8.2 结算批次核销

用于铁路、油料等高频往来单位。财务先选择往来单位和结算期间，将该期间的候选发票和资金加入批次。系统显示：

- 发票合计；
- 资金合计；
- 已分配金额；
- 未分配发票金额；
- 未分配资金金额；
- 日期跨度和明细数量；
- 被其他核销占用的记录。

批次确认后仍生成逐条 `ReconciliationAllocation`，因此可以下钻到每张发票和每笔资金。

### 8.3 候选提示顺序

1. 标准往来单位相同且单笔金额完全一致；
2. 已确认单位别名或代收账户相同且金额一致；
3. 同单位在指定日期窗口内连续多笔资金合计等于发票金额；
4. 同单位多张发票合计等于单笔资金；
5. 金额不等时提示部分核销和剩余差额。

系统不自动确认任何候选，不因金额接近而隐藏差额，也不使用供应商期末余额凑平发票。

## 9. 核销约束

- 所有金额使用 `Decimal`，精确到分；
- 分配金额必须大于零；
- 发票累计有效分配不得超过可核销金额；
- 资金累计有效分配不得超过实际收支金额；
- 销项发票只能与资金流入核销；
- 进项发票只能与资金流出核销；
- 已作废发票不能创建新核销；
- 已核销发票发生红冲时必须进入异常清单，由财务创建反向处理；
- 已被其他批次占用的明细必须明确显示，不允许重复使用；
- 并发修改时以数据库事务和版本检查阻止覆盖。

## 10. 主要页面

### 10.1 导入中心

四个固定入口：销项发票、进项发票、银行流水、微信流水。显示最近导入、有效条数、重复条数、异常条数和处理状态。

### 10.2 人工核销工作台

左侧选择发票，右侧选择资金；顶部筛选方向、往来单位、日期和未核销状态；底部固定显示发票金额、所选资金、核销金额和差额。

### 10.3 结算批次

按往来单位和期间组织高频收付款，支持添加、排除、保存草稿、确认及撤销。

### 10.4 异常清单

至少覆盖：

- 已开票未收款；
- 已收票未付款；
- 已付款未找到发票；
- 已收款未找到发票；
- 单位或代收账户未识别；
- 核销差额；
- 疑似重复导入或重复付款；
- 红冲后仍存在有效核销；
- 长期未核销项目；
- 历史迁移缺失资料。

### 10.5 老板 Dashboard

第一阶段展示：

- 当前银行及微信资金；
- 本月收款和付款；
- 应收未收及逾期金额；
- 应付未付及近期到期金额；
- 每日资金流入/流出折线图；
- 应收账龄环图；
- 应付到期柱状图；
- 未匹配资金、已付款未收票、已开票未收款及疑似重复风险。

Dashboard 只统计已确认导入和有效核销数据，同时标记尚未完成的导入批次，避免把不完整数据显示成完整结果。

## 11. 历史数据迁移

用户选择导入全部历史数据。迁移按年度、按来源分批执行：

1. 盘点每年销项、进项、银行和微信资料；
2. 先导入往来单位和别名；
3. 按年度导入发票和资金；
4. 对每年执行完整性检查；
5. 建立历史结算批次并人工确认；
6. 缺失资料进入待补清单；
7. 资料无法取得的早期项目只能登记为“历史未核销明细”，不得由系统猜测逐笔关系。

## 12. 附件

- 发票 PDF 按发票号码自动关联；
- 无法自动关联的 PDF 进入待认领清单；
- 付款申请、铁路缴款单、供应商结算单可关联到发票、资金、结算批次或核销单；
- 附件保留原文件名、上传人、时间和校验值；
- 删除附件采用失效标记并保留审计记录。

## 13. 错误处理与安全

- 无法识别的模板整批拒绝；
- 少量坏行进入隔离区，不静默跳过；
- 导入、核销、撤销和别名变更使用数据库事务；
- 页面错误信息说明失败原因，但不暴露数据库或服务器内部信息；
- 密码使用框架安全哈希；
- DSM 反向代理提供 HTTPS；
- 应用不需要主动访问外部网络；
- 原始银行账号按角色脱敏；
- 每日备份数据库和附件，默认保留最近 30 天；
- 定期执行恢复演练，确保备份可以实际使用。

## 14. 测试与验收

### 14.1 导入测试

- 覆盖税务平台销项和进项 Excel；
- 覆盖农业银行 XLS；
- 覆盖微信 Excel/CSV；
- 同一文件重复导入不产生重复记录；
- 日期、金额、税号、交易号及中文名称解析正确；
- 异常行可定位到源文件和行号；
- PDF 可按发票号码自动关联。

### 14.2 核销测试

- 一对一、一对多、多对一、多对多；
- 部分核销和跨月核销；
- 逐笔与结算批次产生相同的底层分配结果；
- 同一笔资金不能超额或重复占用；
- 红冲、退款和撤销后可用金额恢复正确；
- 不使用期初或期末余额生成候选关系。

### 14.3 测试铁路物流回归案例

以现有资料建立 2026 年 6 月结算批次：

- 6 月铁路专户付款合计为 47,050.00 元；
- 2026-06-16 的 2,000.00 元付款与 2026-07-07 的 2,000.00 元发票人工核销；
- 剩余 6 月付款为 45,050.00 元；
- 2026-07-07 的 46,050.00 元发票只能先核销 45,050.00 元；
- 系统明确显示发票剩余 1,000.00 元，不得使用 6 月期末余额自动冲平；
- 后续取得缴款单或其他资金证据后，再由财务补充核销。

### 14.4 权限与恢复测试

- 老板无法导入、核销、撤销或查看未授权附件；
- 财务所有关键操作均形成审计日志；
- 数据库和附件备份能够在独立测试目录恢复；
- DSM 容器重建后，持久化数据不丢失。

## 15. 后续扩展

第一期稳定后，可以按优先级增加：

1. 出入库或运输结算单导入，检查应开未开和应收未收；
2. 付款申请和审批；
3. 会计凭证建议及代理会计导出；
4. 银行或税务平台 API；
5. 消息提醒；
6. 移动端适配。

这些扩展均通过现有发票、资金、往来单位、附件和核销接口接入，不改变第一期证据链。
